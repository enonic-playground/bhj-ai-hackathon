### Objective and exit demonstration

A fresh checkout can install dependencies, start the app, display a title screen, and enter a playable maze. A player can navigate with keyboard or touch, queue turns, traverse side tunnels, and collect dots without crossing walls or collecting the same dot twice. Clearing all dots does not finish the level. This is the functional baseline for M2, not yet the complete Hac-Man game.

### In scope

1. **Project foundation:** TypeScript, Vite, Canvas 2D maze rendering, HTML/CSS menus/HUD/controls, Vitest, and a minimal Playwright browser smoke suite. Pin compatible dependencies in a lockfile and document a tested runtime version. Use npm for this initial scaffold unless the repository gains an existing package-manager convention before starting.
2. **Title and instructions:** title, a working Start action, and concise keyboard/touch instructions. Start enters a fresh level-one maze with score zero. No fake playable features or static success screens.
3. **Original maze:** one authored tile map with walls, connected player corridors, a valid player spawn, dots, and paired left/right tunnel exits. The wireframe maze is illustrative; do not copy it as unvalidated level data. Reserve a central enemy-home region for M3 if useful, but keep it inaccessible to the player and implement no enemies yet.
4. **Player movement:** continuous cardinal movement, no diagonal movement, buffered turns at legal junctions, stopping at walls, and tunnel wraparound. Begin stationary until the first direction. Once moving, releasing a key/button does not stop the player; the player continues until a wall or another legal direction. Keep one latest requested direction; an illegal requested turn waits while the current legal movement continues. Allow a reversal in a corridor without wall penetration. Keep speed configurable.
5. **Dots and score:** consume each dot once for 10 points; update visible score. A dot-free maze remains navigable without a level-complete transition. Do not spawn a collectible under an inaccessible tile.
6. **Input:** arrow keys/WASD and a visible directional pad using pointer/touch input. A visible pad is the required M1 mobile path; swipe may be added later. Prevent scrolling for handled movement keys only when the game owns input, and suppress touch gestures only on gameplay controls. Clear stale queued/held input when leaving the play context.
7. **Responsive shell:** keep the maze, score, level/mode label, and directional pad together at 360 × 640 CSS pixels. Use a side panel for desktop hints as appropriate; preserve tile aspect ratio. Touch buttons are at least 44 × 44 CSS pixels. Give menu/control buttons labels and visible focus. A simple original player shape is sufficient.
8. **Deterministic engine:** separate maze/state/movement/dot logic from canvas, DOM, input events, and animation scheduling. Use a fixed simulation step with bounded catch-up; background delays must not teleport the player or replay minutes of movement. Make the simulation directly step-able in tests. Avoid building unused systems for later milestones.
9. **Working documentation:** replace README's “no application” notice when true; document only commands actually established and verified. Describe this milestone's supported behavior and remaining game features. Preserve the accepted project estimates and existing license.

Suggested module boundaries (names are illustrative): maze data/validation, game state and simulation step, movement, input adapters, canvas renderer, application shell, unit/integration tests, and browser smoke tests. Claude may choose a simpler file structure if these boundaries remain testable.

### Out of scope

Ball movement/capture, word selection, guessing UI and level completion (M2); enemies, power pellets, lives/death, full pause/resume and restart flows (M3); fruit, full scoring, extra lives, campaign, high score, persistence and sound (M4); PWA installation/cache/update behavior and final device polish (M5); release cleanup and complete final documentation (M6). Do not render inactive mute, guessing, enemy, or result controls merely to match the full wireframe. Word and lives HUD fields can wait for the corresponding behavior.

A full pause interface is not required in M1. Implement input cleanup and safe timing on focus loss now; document the current behavior, with explicit pause/resume semantics completed in M3. Public hosting, account setup, and deployment are not part of this milestone.
