### Objective and boundaries

Deliver a usable mobile/desktop application that can be installed where supported and can launch and play the complete campaign offline after one successful online preparation. Updates must preserve an active run, including a run in another tab.

In scope: responsive layout and touch refinements, keyboard/focus and readable feedback, system reduced-motion support, original app icons/manifest, production service worker and complete offline assets, safe update lifecycle, retained storage-failure browser tests, installation/recovery documentation and device evidence. Extend the existing shell, renderer, input adapters and build/test setup; keep browser/PWA concerns outside the simulation.

Out of scope: audio/music/sound/mute (excluded permanently), new gameplay, accounts/backend, analytics, saving a run, new mazes, optional swipe gestures when the visible pad suffices, and a new settings panel. Preserve all M1–M4 rules, word/scoring values, ball visibility and default approved enemy feedback. Full release cleanup, remaining fruit-edge regression expansion and three human release runs remain M6; collect useful human pacing observations now if available.

### Implementation contract

1. **Responsive layout and touch.** At 360 × 640 CSS pixels show HUD, square-tile maze and directional pad together in CHASE; A–Z remains usable in GUESS. Support landscape (including 640 × 360), desktop 1280 × 800 and a tall-to-short desktop resize without reload. Account for safe-area insets and changing available height. Do not shrink touch buttons below 44 × 44 pixels or remove the pad on touch landscape. Preserve page gestures outside gameplay controls. Handle interrupted pointers, resize/orientation, blur and background without stuck input, unintended guesses or elapsed-time catch-up. At larger text/zoom, permit vertical scrolling in menus/frozen guessing panels while keeping all actions reachable and avoiding horizontal page overflow. Test long categories, eight-letter words, many misses, five-digit score, four lives/earned-life badge, and both new result panels—not only the starting HUD. Reuse narrow injected/gated fixtures for hard-to-reach UI states; never add production state setters or answer leakage.
2. **Focus and announcements.** Menus/overlays own actionable focus; covered/hidden controls cannot receive Tab input. Maintain visible focus, logical tab order, labeled HTML buttons and non-color-only status. Check title, pause, guess, countdown, death, level-complete, game-over and campaign-complete transitions, including touch switching to keyboard. Retain explicit Resume after returning from background. Word/guess and extra-life feedback must remain understandable without announcing every animation frame. Install/offline/update notices must not steal focus or cover gameplay controls. Full nonvisual navigation of the action maze remains outside scope.
3. **Reduced motion.** Respect `prefers-reduced-motion` on initial load and when it changes. Apply it to canvas effects as well as CSS. In reduce mode use a stable contrasting ball fill with its white ring, steady pellet/shield indicators, a nonflashing frightened-expiry cue, and suppress optional decorative oscillation/transitions; essential actor movement remains unchanged. In normal mode retain D015's smooth 2,000 ms active-time hue cycle and owner-approved frightened warning. Presentation changes must not affect speed, timers, input, collision or scoring. No persisted preference/UI toggle is necessary; use the OS preference. Test both modes and changing preference while paused/guessing without advancing the maze.
4. **Install metadata and assets.** Provide manifest name/short name, stable app identity, scoped start URL, standalone display, suitable colors and correctly sized original icons (192/512 PNG plus a maskable asset and Apple touch icon where used). Verify actual dimensions and safe artwork placement. All URLs must resolve within the deployed app path; installed launch returns to TITLE, not a saved run. Avoid copyrighted game artwork and external fonts/CDNs. Keep installation progressive: ordinary browser play works if install or service-worker APIs are unavailable. Offer concise title-screen install help; show an install action only when the browser supports the corresponding prompt. Do not invent a universal install dialog. Verify current platform-specific instructions during implementation and document tested browser/OS versions.
5. **Complete offline preparation.** Register the worker only for ordinary production output. Precache a coherent version of the shell, all required JS/CSS, bundled words, artwork, icons and manifest; build-derived asset enumeration must follow hashed filenames. A successful first online load must be enough to prepare the entire five-level run, not only the currently visited level. Define readiness from successful installation/cache completion, not `navigator.onLine` or registration alone; show a quiet ready/unavailable status on the title screen. Test offline reload and a fresh page launch in the same prepared browser profile, then play. First-ever offline visits cannot install uncached assets; document that limitation and possible browser cache eviction. Worker/CacheStorage failure must leave online play functional and must not falsely claim offline readiness. Cache only appropriate app-local GET requests, scope navigation fallback to the application, and do not answer missing scripts/icons with HTML. Namespace caches by app path and version; never delete unrelated origin caches or local high score.
6. **Safe version updates.** Install a new complete version into separate caches; a failed/partial download leaves the prior playable version intact. No unconditional `skipWaiting`, reload-on-controller-change or automatic reload during play. For this milestone, prefer the native waiting lifecycle: notify at TITLE or after GAME_OVER/CAMPAIGN_COMPLETE, explain that closing all Hac-Man windows and reopening applies the update, and activate when old controlled clients are gone. LEVEL_COMPLETE is mid-run and PAUSED retains an active run; neither is a safe forced-reload boundary. Keep old assets usable until no client needs them. If choosing an explicit Update now action instead, document and test coordination with every controlled tab/window; a hidden, unresponsive or active client must defer activation. A title tab must never discard another tab's run. Newly activated versions must launch coherently and work offline. Keep worker URL stable; version content/caches instead. Do not cache the worker script via its own application asset fallback.
7. **Storage and build isolation.** Retain committed browser regressions for a throwing localStorage getter and quota-exceeded writes: game starts/scores, in-memory best survives return to title, reload returns to title without crashing, and normal/corrupt persistence still works. Preserve M4's stale-tab score regression. Dev and fixture builds must not register the production worker; use separate origins/profiles for fixture and production checks so an old worker cannot disguise a broken build. Ordinary production must still contain no fixture parameter controls. Any new PWA build tooling must be pinned, documented and covered by the lockfile; avoid unrelated upgrades.
8. **Documentation and evidence.** Update README for actual install paths, first-online preparation, offline behavior, pending updates, app-specific cache recovery (including whether clearing site data loses best score), build/preview/test commands, architecture and limitations. Use `docs/evidence/m5/` for new screenshots; preserve accepted M1–M4 evidence. Record exact browser/device/OS, viewport, build SHA, manual versus automated steps, observed results and unavailable checks. Check smoothness on a representative laptop and phone and record observations without claiming measured 60 fps from emulation. Record any human first-capture/per-level/run timings separately from scripted timings; PRD targets remain unchanged.
